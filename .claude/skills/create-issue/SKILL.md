issueを作成する。起動後は途中で確認を挟まず最後まで実行してよい。
ただし手順1で既存issueが見つかった場合は例外で、作成せずにコメント追加を提案してユーザーの判断を仰ぐ。

## 手順

1. `gh issue list --search "<キーワード>" --state all` で重複を確認する
   - 既存issueがあれば、新規作成せずコメント追加を提案する
2. 種類に応じてテンプレートと同じセクション構成で本文案を作る
   - バグ報告: `.github/ISSUE_TEMPLATE/bug_report.yml`
   - 機能要望・タスク: `.github/ISSUE_TEMPLATE/feature_request.yml`
3. 本文を一時ファイルに書き、`gh issue create --title "<タイトル>" --body-file <ファイル> --label <ラベル>` で作成する
   - `--label` を必ず明示する。テンプレートの `labels:` には頼らない
4. 作成したissueのURLと、登録した本文をユーザーに伝える

## タイトル

Conventional Commits形式。一覧で見て中身が分かる解像度にし、`ログインできない` `改善` のような曖昧なタイトルにしない。
type は内容に合わせて選ぶ（バグ報告は `fix`、機能要望は `feat`、保守作業は `chore` や `refactor` など）。

```
fix: パスワード未入力時にログインAPIが500を返す
feat: 月次レポートのCSVエクスポートを追加する
```

## 本文の方針

- 1 issue = 1 トピック。複数の課題が混在する場合は分割してから作成する
- 完了条件を必ず書く。「何ができたら閉じてよいか」が無いissueを作らない
- 機能要望では、解決策より先に「課題」を書く。実装方針だけを書かない
- バグ報告の再現手順は、実際に再現を確認した手順だけを書く。未検証ならその旨を明記する
- 環境情報は実際に確認した値のみ記載する
- 原因の見当は「推測」セクションに分け、ログやエラーメッセージと混ぜない

## ラベル

リポジトリに存在するラベルだけを使う。`gh label list` で名前と説明を確認し、内容に合うものを選ぶ。
新しいラベルを勝手に作らず、必要なら提案する。
